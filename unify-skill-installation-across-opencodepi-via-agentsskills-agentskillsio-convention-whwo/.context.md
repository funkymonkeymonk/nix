# Goal
Collapse skill installation from 3 separate per-agent directory trees (opencode, pi, and unused claude-code) down to ONE canonical install location -- ~/.agents/skills/<name>/SKILL.md -- following the vendor-neutral Agent Skills convention (agentskills.io), not Claude Code's own paths.

# Why
## The agentskills.io spec does NOT mandate a discovery location
Verified via https://agentskills.io/specification -- it only standardizes the SKILL.md frontmatter format (name, description, license, compatibility, metadata, allowed-tools) and per-skill directory layout (scripts/, references/, assets/). Filesystem discovery location is entirely client-defined.

## ~/.agents/skills/ is read NATIVELY by opencode AND pi, with ZERO config
- OpenCode docs (opencode.ai/docs/skills): checks '.agents/skills/<name>/SKILL.md' (project) and '~/.agents/skills/<name>/SKILL.md' (global) -- listed explicitly as 'agent-compatible' paths, separate from its own '.opencode/skills/' paths.
- Pi docs (github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/skills.md): lists '~/.agents/skills/' as a GLOBAL location, loaded with no settings.json entry required. (Contrast: pi does NOT read ~/.claude/skills/ natively -- that requires an explicit 'skills' array entry in settings.json. ~/.agents/skills/ needs nothing.)
- Claude Code does NOT read ~/.agents/skills/ at all, and has no 'extra directories' setting to add it. This is fine -- no host in this repo enables roles.claude, so Claude Code is explicitly NOT a target of this unification.

## Zero functional loss: all 3 agent modules already install the IDENTICAL skill set
Verified via grep: modules/home-manager/{opencode,claude-code,pi-coding-agent}.nix each call hmLib.mkFullSkillDirs { enabledRoles = skillsCfg.enabledRoles or []; } with the SAME globally-derived osConfig.myConfig.skills.enabledRoles (modules/roles/default.nix:31). There is no existing per-agent skill differentiation for internal/superpowers skills -- just 3x duplicated physical copies of the same content, written via 3 separate home.file codepaths.

## Current state (verified via live nix eval against darwinConfigurations.wweaver)
```
/Users/wweaver/.config/opencode/skills/<name>   <- opencode, absolute path, own home.file wiring
.pi/agent/skills/<name>                          <- pi, relative path, own home.file wiring
(claude-code: unused on any host, but its home-manager module targets ~/.claude/skills/<name> if it were used)
```

# Design
1. New module modules/home-manager/skills/canonical-install.nix: computes enabledRoles from osConfig.myConfig.skills.enabledRoles (same source as today), calls the EXISTING hmLib.mkFullSkillDirs helper (modules/home-manager/lib.nix:118) to get skillDirs, and writes home.file.".agents/skills/${name}" = { source = dir; } for each -- a plain symlink into the Nix store (home-manager's home.file with 'source' is a symlink by default, no special handling needed).
2. This module is gated on 'any skill-consuming role enabled' (i.e. skillsCfg.enabledRoles != []), NOT on any single agent's role.enable -- it should not live inside opencode.nix, claude-code.nix, or pi-coding-agent.nix.
3. modules/home-manager/opencode.nix: remove its own mkFullSkillDirs call + home.file writes for internal/superpowers skill DIRECTORIES (the '.config/opencode/skills/<name>' entries). KEEP whatever is unique to opencode: the auto-loaded.md digest file and mkSkillCommands (/finish, /pr, /push-style slash commands) -- these are opencode-specific features beyond plain SKILL.md discovery and need their own resolution (see Open Questions).
4. modules/home-manager/pi-coding-agent.nix: remove its mkFullSkillDirs call + home.file writes for '.pi/agent/skills/<name>' entirely. Pi discovers ~/.agents/skills/ automatically, no settings.json change needed.
5. modules/home-manager/claude-code.nix: leave untouched -- out of scope, not a unification target, not currently used by any host.
6. External skills (npx skills add --agent X, in modules/home-manager/skills/install.nix) are unaffected by this yak -- that mechanism is inherently tool-specific (fetches agent-formatted content over the network) and is a separate concern from internal/superpowers skill placement.

# Open Questions (resolve during implementation, or flag back if blocked)
- opencode's auto-loaded.md digest (modules/home-manager/opencode.nix:277) currently references specific skill file paths for 'autoLoad = true' skills, forcibly injected into opencode.json's instructions list (bypassing the on-demand skill tool). Once skill dirs move to ~/.agents/skills/, does this digest generation still have everything it needs (yes, in principle -- it can reference ~/.agents/skills/<name>/SKILL.md directly), or does it need adjustment? Verify auto-loaded skills still get injected correctly after the move.
- mkSkillCommands (modules/home-manager/lib.nix:167, used for jj's /finish /pr /push and yak-shaving's /shave) maps skill-bundled commands into home-manager's programs.opencode.commands option. This is independent of skill DIRECTORY placement (it reads from skill.commands.path in the manifest directly, not from the installed skills dir) -- confirm it keeps working unchanged.
- Should home-manager instead use lib.hm.file.mkOutOfStoreSymlink, or is a plain home.file source= symlink sufficient? Plain source= should be fine since these are store paths already, not out-of-store paths -- verify no home-manager assertion complains about the target already existing from a prior generation (standard home-manager file-management should handle this like any other home.file entry).
