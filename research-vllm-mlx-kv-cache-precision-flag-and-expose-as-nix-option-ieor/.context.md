## Why
The source article lists "KV cache precision" alongside MTP speculative decoding
and chat-template handling as one of the launch flags that "separate a sluggish
setup from one running 2-3x faster on identical hardware." Today,
modules/services/vllm-mlx/instance-options.nix has NO kv-cache-precision option
at all, and lib.nix's CLI-flag builder (`vllmMlxWrapper`, lines ~138-166) doesn't
pass any such flag. This is a genuine capability gap, not just a tuning knob --
worth confirming upstream support before promising a Nix option.

## What to do
1. Check `vllm-mlx serve --help` / upstream waybarrios/vllm-mlx source
   (packages/vllm-mlx/default.nix pins commit 61c78dc0) for a KV-cache dtype/
   precision flag (commonly named `--kv-cache-dtype`, `--kv-bits`, or similar in
   MLX-based servers; MLX supports int8/int4 KV cache quantization natively)
2. If it exists: add `kvCachePrecision` (nullOr enum ["fp16" "int8" "int4"] or
   whatever upstream actually calls it) to instance-options.nix, wire it into
   lib.nix's flag builder the same way `maxKvSize` is wired
      (`lib.optionalString (instanceCfg.kvCachePrecision != null) "--<flag> ${instanceCfg.kvCachePrecision}"`)
3. Write a Nix eval test in tests/test-vllm-mlx.nix asserting the flag appears
   in the generated launchd command when set (follow existing test patterns for
   maxKvSize/enableMtp)
4. On MegamanX, benchmark int8 (or whatever's supported) KV cache vs current
   fp16 default: memory savings should let maxKvSize (see the companion
   "Raise maxKvSize" yak) go even higher within the same memoryBudgetGb, and/or
   improve tok/s
