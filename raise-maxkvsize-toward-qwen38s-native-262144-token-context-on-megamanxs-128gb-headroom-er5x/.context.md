## Why
Qwen3.8-27B natively supports a 262,144-token context window (per source
article). MegamanX's current config (hosts/megamanx/default.nix:40) caps
maxKvSize at 131,072 — exactly half — while only 88GB of the machine's 128GB is
budgeted across both vllm-mlx instances (64GB qwen + 24GB gemma), leaving ~40GB
of headroom unused. On a 128GB Studio dedicated to this stack, that's likely
leaving real long-context agentic capability on the table (very long repo/tool
context, long-running pi/opencode sessions) without needing to touch the other
instance.

## What to do
1. Measure actual KV-cache memory cost per additional 1k tokens for
   Qwen3.8-27B-8bit at current settings (can be estimated from vllm-mlx logs or
   by binary-searching maxKvSize upward while watching memory_budget_gb
   eviction behavior under `contention = "preempt"`)
2. Increase `maxKvSize` in hosts/megamanx/default.nix stepwise (e.g. 131072 ->
   196608 -> 262144) and increase `memoryBudgetGb` from 64 if needed to avoid
   evicting the model itself before hitting the ceiling
3. Confirm the gemma instance (port 8301, separate 24GB budget) is unaffected
4. Watch for the documented crash risk: prefix-cache + prompts >19k tokens
   (vllm-mlx#178) — NOT applicable to the qwen instance today since it doesn't
   use `enableContinuousBatching`/`enablePrefixCache`, but note this constraint
   if the "batched instance" or "MTP+batching" companion yaks change that later

## Acceptance criteria

- [ ] hosts/megamanx/default.nix updated with the new value + a comment
