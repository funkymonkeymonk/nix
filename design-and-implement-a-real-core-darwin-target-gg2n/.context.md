# Goal
Make 'core' the shared source of truth between devenv.nix's own dev shell and the foundation (+ developer) roles real machines use -- eliminating the separately-maintained library/dev-base.nix package list, which has already drifted from modules/roles/foundation-packages.nix. devenv.nix should consume the SAME role package definitions that real Darwin/NixOS machines do, not a hand-maintained parallel list.

# History (why this needs care, not a naive redo)
'core' existed originally (Phase 5, commit 9b4686f/#312), was replaced by 'core-v2' (a deliberately minimal, secrets-free, home-manager-free target importing library/dev-base.nix -- commit 5e30f36/#360: 'No secrets, no machine-specific services, no home-manager'), then core-v2 was deleted entirely during recent cleanup (a6aaf47, 'Begin deprecating old systems') as likely-dead scratch code. library/dev-base.nix and modules/darwin/dev-base.nix still exist on disk, orphaned -- only devenv.nix itself still imports library/dev-base.nix (devenv.nix:2). This is the third attempt at 'core' -- get the actual purpose right this time (see Goal above, confirmed with Will 2026-08-23) rather than recreating another scratch target that gets deleted again.

# Verified package drift between library/dev-base.nix and modules/roles/foundation-packages.nix
- In dev-base but NOT in foundation's common list: gh-dash (actually lives in modules/roles/developer.nix, not foundation), eza, alejandra, statix, deadnix, nix-tree, nvd, nixd (the last 6 are flake-hacking/Nix-linting tools, arguably devenv-only, not relevant to end-user machines running the foundation role)
- In foundation's common list but NOT in dev-base: rclone, himalaya, zinit, zsh, antigen
- Conclusion: devenv's shell is closest to 'foundation + developer' roles, MINUS a few foundation packages not needed for flake-hacking (himalaya/zinit/antigen), PLUS a handful of Nix-tooling-specific extras (alejandra/statix/deadnix/nix-tree/nvd/nixd/eza) that don't belong in either role since they're for developing THIS flake, not for end-user machines.

# Design
1. devenv.nix imports modules/roles/foundation-packages.nix directly (it's a plain {pkgs}: {common=[...]; darwinOnly=[...];} function, zero module-system dependency, trivially reusable outside NixOS/Darwin -- confirmed by reading it) instead of library/dev-base.nix.
2. Nix-tooling-only extras (alejandra, statix, deadnix, nix-tree, nvd, nixd, eza) stay defined directly in devenv.nix as devenv-specific additions layered on top of the role's package list -- NOT duplicated into modules/roles/foundation-packages.nix or developer.nix.
3. Reconcile the real drift: decide whether gh-dash's home is developer.nix (current) or should also apply to devenv (add to devenv.nix's extras if wanted, don't move it into foundation).
4. New darwinConfigurations.core built from library/archetypes/base-darwin.nix (WITHOUT its home-manager/opnix wiring -- that contradicts the 'no secrets' goal; may need a trimmed variant or a new minimal archetype) + myConfig.roles.foundation.enable = true (+ developer.enable = true, matching devenv's actual tool set most closely per the drift analysis above).
5. core is a BUILD/EVAL-only smoke-test target, never switched to on real hardware -- foundation.nix unconditionally sets myConfig.onepassword.enable = true, which is fine for build/eval (no real 1Password session needed to evaluate or build the derivation, only to actually activate/switch it).
6. Delete library/dev-base.nix and modules/darwin/dev-base.nix once devenv.nix and core both source from the real role system -- they become fully redundant.
7. Update modules/common/scripts/nix-cloud-init if 'core' should be offered as a provisionable target (per the parent Phase 8 yak's data-driven-target-list goal) -- confirm with Will whether core should be user-provisionable or purely a CI/devenv-internal concept.

# Acceptance Criteria
- [ ] devenv.nix sources its package list from modules/roles/foundation-packages.nix (+ developer.nix's list, or a documented subset) instead of library/dev-base.nix
- [ ] devenv-only Nix-tooling extras (alejandra, statix, deadnix, nix-tree, nvd, nixd, eza) remain defined in devenv.nix, clearly separated from role package lists
- [ ] darwinConfigurations.core added to flake.nix, built with foundation (+ developer) roles enabled, no secrets/home-manager required to build/eval
- [ ] library/dev-base.nix and modules/darwin/dev-base.nix removed once no longer referenced
- [ ] devenv shell (devenv shell / direnv) still provides every tool it did before -- diff the package list before/after to confirm no regression
- [ ] nix build .#darwinConfigurations.core.system succeeds without any real secrets/1Password session present
- [ ] devenv tasks run check:lint && devenv tasks run test:all pass
- [ ] Decide and document (in this yak or a follow-up) whether core should be provisionable via nix-cloud-init, or stays purely internal/CI-only
