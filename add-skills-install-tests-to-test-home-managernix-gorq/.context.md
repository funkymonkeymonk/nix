# Goal
Add eval-level tests to tests/test-home-manager.nix that verify skill directories actually get wired into home.file correctly per-agent, replacing the closed VM-based approach (test-skills-e2e.nix). Implements US-025 (prd.json).

# Why eval-level, not VM
External skills (npx skills add) need live network access at activation time -- a sandboxed VM test can't verify that path either. Internal/superpowers skills are wired via home-manager's native programs.<agent>.skills option, which IS fully static/declarative -- verifiable via lib.evalModules, no boot needed.

# Empirically-verified structure (nix eval against real darwinConfigurations.wweaver -- do NOT assume, these differ per agent):
```
$ nix eval ".#darwinConfigurations.wweaver.config.home-manager.users.wweaver.home.file" --apply "..."
"/Users/wweaver/.config/opencode/skills/brainstorming"   <- opencode: ABSOLUTE path key
".pi/agent/skills/brainstorming"                          <- pi: relative path key, DIFFERENT base dir
".config/opencode/skills/auto-loaded.md"                  <- unrelated digest file, not a skill dir, skip
```
- Each home.file entry maps a skill name to a SOURCE DIRECTORY (not a SKILL.md leaf file) -- home-manager copies/links the whole dir. 'SKILL.md installed' means: the entry's source directory contains a SKILL.md, checkable via builtins.pathExists "${source}/SKILL.md" at eval time (no IFD -- these are plain repo-local paths for internal skills).
- opencode uses ABSOLUTE keys (${home.homeDirectory}/.config/opencode/skills/<name>); pi uses RELATIVE keys under a different base (.pi/agent/skills/<name>). claude-code's scheme has NOT been verified yet -- check modules/home-manager/claude-code.nix + a real eval the same way before writing assertions for it.
- myConfig.skills.enabledRoles is NOT set manually -- it's auto-derived in modules/roles/default.nix:31 from whichever myConfig.roles.<x>.enable flags are true. Tests should enable roles (e.g. myConfig.roles.opencode.enable = true) and let that flow through naturally, matching real hosts -- not hand-set enabledRoles.

# Why this is more than 'add a checkbox to an eval test'
Every existing test in tests/test-home-manager.nix (stubs.base) only evaluates OS-level option DECLARATIONS in modules/common/options.nix -- none currently evaluate the actual home-manager module that consumes osConfig and produces home.file. This yak requires a NEW stub composition (add to tests/stubs.nix, following its existing composition-rules doc comment):
- Fakes osConfig via specialArgs (needs at minimum myConfig.skills.enabledRoles, myConfig.onepassword.enable)
- Pulls in home-manager's actual upstream programs.opencode module (from the home-manager flake input) plus this repo's modules/home-manager/opencode.nix
- Stubs baseline home-manager options those modules assume exist (home.homeDirectory, home.stateVersion)
