# Declarative API Reconciliation

Some services expose their process configuration to NixOS, but keep the settings users change in a web UI inside a database. A NixOS generation can install and start such a service without reproducing its download clients, root folders, integrations, profiles, or other API-managed objects. If those settings are left in the UI, a rebuilt host depends on unrecorded state and configuration drift is difficult to repair.

API reconciliation provides a boundary between Nix's desired configuration and an application's persistent state. Nix declares the values that this repository owns. A small service-specific adapter reads the live application state through its supported API and makes those declared values true. It does not replace the application's database or assume that every field in the database belongs to Nix.

## Choose the right configuration layer

Use the least complex supported layer for each setting:

1. **Native NixOS option:** use it for service lifecycle, systemd behavior, ports, directories, and application settings the module supports. Check whether values are copied into the world-readable Nix store before putting secrets there.
2. **Runtime configuration file:** use a generated file when the application has a documented file format and reads it at startup. Generate it at runtime if it contains secrets. Overlay only the declared keys on an existing file when migrating user state.
3. **Application API:** use it for settings held in a database or requiring application validation. Prefer an app-supported API over editing SQLite or another internal database.

Do not use an API merely because it exists. Native options are simpler for static process settings, while a database-backed setting generally needs the application API or a supported runtime file.

## Reconciliation lifecycle

A reconciliation service should:

1. Be declared beside the service configuration, with typed desired-state options.
2. Start after the application is healthy and its API key is available. A systemd oneshot is appropriate for a bounded configuration pass.
3. Read secrets from runtime files. Nix-generated JSON may contain file paths but must not contain secret values. Do not put credentials in command-line arguments or logs.
4. Read the current API object and identify the managed resource by a stable, unique key such as a declared name or endpoint/path pair.
5. Create a missing resource using the service's schema/defaults, or update only the declared fields of the uniquely matching resource. Preserve server-generated IDs and fields Nix does not own.
6. Fail without mutation if the API is unavailable, the schema changes, the secret is missing, or the identity is ambiguous.

The media integration follows this model: Radarr, Sonarr, and Lidarr reconcile the Transmission download client, local root-folder entries, and remote path mapping. Adding a root-folder entry does **not** rewrite existing series/movie/artist paths or move files; that one-time cutover must use the app's supported migration operation and be verified separately. Bazarr has a separate adapter for its Sonarr/Radarr connections because its API contract differs. Mylar3 uses its documented INI config instead of being forced into a Servarr API abstraction.

## Ownership and deletion

A declarative list does not automatically mean that every unlisted item should be deleted. During migration, application databases may contain monitored items, profiles, custom formats, histories, tags, or UI settings that have not yet been represented in Nix. Treat reconciliation as additive/update-only unless the service has a separately designed, explicitly enabled prune operation.

Use a clear ownership key for each managed resource. If two existing resources match, stop and require an operator to resolve the ambiguity. If Nix manages a resource's fields, preserve unrelated fields; do not rebuild an entire database record from a partial Nix value unless the application's schema explicitly requires that behavior.

## Secrets and local APIs

Prefer runtime secret files, such as files materialized by the machine's existing Opnix integration. A sync process should receive only the paths to those files in its store-backed configuration and read their contents when it runs. API keys generated by an application can be extracted from its own runtime configuration into a restrictive file for dependent local services. Give the consumer only the group membership it needs.

Use a loopback address when the reconciler runs on the same host as the target API. The local Arr API ports in the media stack remain restricted to the Tailscale interface for remote Prowlarr connectivity; the reconciliation helper does not open a new firewall route. A remote app owned by another host is a separate configuration boundary and should not be silently mutated from this host.

## Testing the pattern

Test both the API behavior and the Nix wiring:

- Use an in-process HTTP server to test create, update, no-op, schema defaults, field preservation, ambiguous identities, API errors, and that no DELETE request is made.
- Test secret expansion with temporary files and verify that failures/logs do not reveal their contents.
- Use Nix evaluation assertions for systemd ordering, service users/groups, declared resource values, secret file paths, and firewall boundaries.
- Keep application-specific adapters small and test them against the exact API payloads they send.
- Never call a live seedbox or destructive application endpoint from a build test.

## Extending reconciliation to another service

First determine where the service stores the setting and whether its API supports a stable read/create/update flow. Then add typed Nix options, a service-specific adapter, and a oneshot with an explicit readiness/API-key dependency. Add tests for the resource identity and preservation rules before implementation. Document which state Nix owns and which state remains user-managed. If the service only supports a documented startup file, prefer a runtime file renderer over an API client.

## Current media stack boundary

This repository's first reconciliation adapters cover the Drlight-owned Arr/Bazarr/Mylar3 configuration required for migration. They do not claim that every setting or the full application database is declarative. Prowlarr stays on Ultra and its application connections remain an operator-managed step at its own deployment boundary. Application profiles, custom formats, language choices, and catalog contents remain preserved from migrated state until their desired values are explicitly recorded.
