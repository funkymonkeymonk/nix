## Problem
Discovered while migrating skills management (2026-07-26): `modules/roles/opencode.nix`
never sets `myConfig.opencode.enable = true`, unlike `modules/roles/pi.nix` which
explicitly sets `myConfig.pi.enable = true`. This means the home-manager module
`modules/home-manager/opencode.nix` (which manages `.config/opencode/opencode.json`,
skills, commands, RTK integration, etc. via `programs.opencode`) never actually
activates for hosts that only set `roles.opencode.enable = true` without ALSO
separately setting `myConfig.opencode.enable = true`.

## Evidence
- `hosts/wweaver/default.nix` sets `roles.opencode.enable = true` and configures
  `myConfig.opencode.model`, `.disabledProviders`, `.extraMcpServers`, implying the
  author believed the home-manager module was active — but `myConfig.opencode.enable`
  is `false` there (verified via `nix eval .#darwinConfigurations.wweaver.config.myConfig.opencode.enable`).
- Hosts/archetypes that DO work correctly set `myConfig.opencode.enable = true`
  explicitly at the host/archetype level, separately from the role:
  `targets/darwin-server/default.nix`, `targets/type-darwin-server/default.nix`,
  `targets/zero/default.nix`, `library/archetypes/headless-server-darwin.nix`.
- `claude.nix` role has the same gap for `myConfig.claude-code.enable` (not
  verified against a real host since no host currently enables the claude role).

## Likely Fix
Add `myConfig.opencode.enable = true;` to `modules/roles/opencode.nix`'s config
block (mirroring `myConfig.pi.enable = true;` in `pi.nix`), and the equivalent
`myConfig.claude-code.enable = true;` to `modules/roles/claude.nix`.
